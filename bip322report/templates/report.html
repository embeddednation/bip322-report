4. How a proof of control works

{% set m = t.muted %}{% set k = t.ink %}{% set st = t.strong %}{% set ln = t.rule_strong %}{% set mono = t.font_mono %}{# the stacks are escaped in attributes: their quotes would end one #} {# the figure's grid, in the units of its viewBox: three columns of boxes (the left edge of each) and two rows (their top); the lines of text inside a box, and what sits between the boxes, are placed by hand from these #} {% set left = 1 %}{% set mid = 191 %}{% set right = 454 %}{% set top = 50 %}{% set low = 270 %} {% set narrow = 166 %}{% set wide = 246 %}{# the width of a box in the left column, and in the other two #} {% set pad = 10 %}{% set indent = 55 %}{% set step = 22 %}{# from a box's edge: its text, a field's name, a numbered step's second line #} {% set value_dx = 81 %}{# from a field's name to its value: 15 characters of the 9px mono, the longest name ("scriptSig OP_0") and a space #} {% macro val(x, y, text, role) -%} {{ text }} {%- endmacro %} {% macro pill(x, y, w, text, size=8.5) -%} {{ text }} {%- endmacro %} {% macro field(x, y, name, text, role=None) -%} {{ name }}{% if role %}{{ val(x + value_dx, y, text, role) }}{% else %}{{ text }}{% endif %} {%- endmacro %} {% macro txbox(x, y, h, title, sub) -%} {{ title }} {{ sub }} input output {%- endmacro %}

A proof of control is a spend that can never happen: a made-up transaction locks nothing to the real UTXO's scriptPubKey, a second one spends it with exactly what a real spend would need, and that unlocking data is the proof. The mechanism is the same for every kind of scriptPubKey.

{% set S = 'scriptPubKey' %} {% set H = 'hash of the message' %} {% set X = 'txid of to_spend' %} {% set P = 'proof' %} {% set U = 'UTXO' %} {% set B = 'block' %}

Coins and locks. A balance is a set of unspent transaction outputs, {{ U | safe }}s. Each was created by a transaction paying an amount to a {{ S | safe }}, the lock a later transaction must open to spend it, and is named by that transaction's id and the output's index. Whoever can open the lock controls every {{ U | safe }} behind it, so control is a property of the {{ S | safe }}, and that is what a proof is about. Locks come in several kinds, a single key, a script, a taproot output; the proof works the same way for all of them.

The message. The text on each {{ U | safe }} page: a title, and a line naming a {{ B | safe }} by height, hash and time. A block's hash cannot be known before the block exists, so the proof is no older than that {{ B | safe }}. The message is hashed (SHA-256 under the tag BIP0322-signed-message), and the {{ H | safe }} is what enters the transactions.

Two transactions that never reach the network. to_spend has an output with the same {{ S | safe }} as the real {{ U | safe }} and nothing in it, and an input that spends no coin at all, the null outpoint, carrying the {{ H | safe }}. to_sign spends that empty output, naming it by the {{ X | safe }}, and pays nothing to OP_RETURN, which no one can spend. Neither can ever be confirmed, since the coin they pass along does not exist: a proof cannot move funds.

The {{ P | safe }}. to_sign's input must be unlocked like any spend from that {{ S | safe }}, so the signers produce its witness, exactly what a real spend would carry; every signature in it commits to the {{ X | safe }}, and through it to the message. That witness, base64-encoded with the prefix smp (BIP-322's simple format), is the {{ P | safe }}. Nothing else needs to be kept: the verifier rebuilds both transactions from the message and the {{ S | safe }}.

Verification. The verifier rebuilds to_spend from the {{ H | safe }} and the {{ S | safe }}, rebuilds to_sign from the {{ X | safe }} with the {{ P | safe }} as its witness, and checks that input exactly as a node validating a block would: the {{ P | safe }} must unlock the {{ S | safe }} under the rules that govern every spend, whatever kind of lock it is. That is the verify command on each {{ U | safe }} page. The lookup beside it finds the {{ U | safe }} in the chain's set of unspent outputs, with its amount and the same {{ S | safe }}. The engines named in each output make the check independently; one of them is Bitcoin Core's own consensus library.

What it shows. That at the {{ B | safe }} named in the message the holder could produce a valid spend from the {{ S | safe }}, which is what controlling the {{ U | safe }}s locked to it means; a {{ U | safe }} confirmed after that {{ B | safe }} is covered by a later {{ P | safe }}. Control, not title: not who owns the coins, nor what liabilities stand against them. Nothing about any time after the {{ B | safe }}; a new {{ P | safe }} over a new {{ B | safe }} does.
